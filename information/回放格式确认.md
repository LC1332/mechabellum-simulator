## 结合实际回放数据的结论

结论不是简单的“是”或“否”：`.grbr` 确实在每个
`PlayerRoundRecord/playerData` 中保存了一份累计状态快照，但它不是完整的
Markov state。大部分经济、专家、科技、技能 CD 和单位状态都被总结了；其中
`supply` 是经济字段，`reactorCore` 是玩家当前的核心血量。战斗报告里的
`Score` 则是该场战斗造成的扣血量，不是当前剩余血量。

我检查了 `local_data/human_replay/*.grbr` 中的回放。所有回放的 `playerData` 都有
以下 20 个顶层字段：

```text
randomStateData, reactorCore, supply, preRoundFightResult,
units, unitIndex, officers, commanderSkills, activeTechnologies,
equipmentDatas, shop, contraptions, contraptionIndex, bluepints,
researchQueue, energyTowerSkills, towerStrengthenLevels,
constructionSnapshotDatas, constructionIndex, IsSpecialSupply
```

### 对照问题逐项确认

| 想要的状态 | 回放字段 | 结论 |
|---|---|---|
| 回合数 | `PlayerRoundRecord/round` | 有；原始回放从 0 开始计回合。 |
| 玩家血量 | `playerData/reactorCore`；战斗报告有 `FightReport/Score` | 有。`reactorCore` 是当前剩余核心血量，`Score` 是本场对对手造成的扣血量；相邻回合可以用二者互相核对。 |
| 当前经济 | `supply`，以及 `shop` 内的购买/解锁计数 | 有。`supply` 是经济；4000 多的 `reactorCore` 数值不是经济，而是核心血量。 |
| 所有专家 | `officers` | 有。它是累计 ID 列表，不是只记录本回合新增的专家。 |
| 是否拥有全局 buff | 没有单独的 `globalBuffs` 布尔值；主要分散在 `officers`、`bluepints`、`towerStrengthenLevels`、`activeTechnologies`、`commanderSkills` 等字段 | 大部分有状态表达，但需要按 ID 和字段解释。不能只找一个统一的 buff 列表。 |
| 所有单位 | `units` | 有，包含 `id`、`index`、`RoundCount`、`Durability`、`Exp`、`Level`、位置、装备、朝向、回收价格等。它是本回合部署动作发生前的快照；死亡单位在下一回合不会从 `units` 中删除，因此 `units` 更接近持久化的单位/卡片记录，不能仅凭是否存在判断本回合是否存活。 |

### 两个例子的实证

`ChooseReinforceItem` action 和后续快照的关系符合预期：

- 选择 `10004`（额外部署位）时，本回合的 `officers` 还没有它；下一回合的
  `officers` 出现 `10004`，之后的回合继续保留。全量回放中有 337 个有下一回合
  快照的该选择，337 个下一回合都包含 `10004`。
- 选择 `32301`（改进型沙虫）的 4 个样本中，下一回合的 `officers` 都出现了
  `32301`，并在后续快照中继续存在。

因此，针对这两个“永久拥有”的增援/全局效果，不需要从第一回合重新扫描 action
才能知道玩家已经拥有它们；下一回合的快照已经做了冗余总结。

### 关于 `reactorCore`、`supply` 和 `Score`

你这次的判断是对的：`supply` 是经济，4000 多的 `reactorCore` 是玩家当前的
核心血量。原始回放中的 `<Score>` 只出现在
`matchDatas/MatchSnapshotData/lastFightResult/Reports/FightReport`，表示一场战斗
对对手造成的扣血量。

这不是把两个玩家的数据混在一起造成的误解。原始文件把双方放在不同的
`PlayerRecord` 下；核验时也是在每个 `PlayerRecord` 自己的回合列表内比较相邻值。
以同一局为例，某玩家的 `reactorCore` 依次为 `4700 -> 4240 -> 3940`，对应对手
报告的 `Score` 分别为 `460`、`300`，正好满足：

```text
hp_next[player] = hp_current[player] - opponent_report.Score
```

全量 1106 局中，能和双方 `FightReport` 对齐的 13222 个玩家回合全部精确匹配。

唯一集中出现的“上升”是初始化边界：20282 条快照的相邻值中，
`reactorCore` 上升 1298 次、下降 7930 次、持平 8378 次；1298 次上升全部是
`round 0 -> round 1`，例如 `4500 -> 4700`、`4500 -> 5000`、`4500 -> 5200`。
这对应开局选择/初始血量修正应用后的状态，不是从玩家 A 串到了玩家 B。官方更新说明
也确认过开局选择会带来不同的初始 HEALTH 修正。

因此，1v1 下可以把 `reactorCore` 作为当前血量、把对手 `FightReport.Score` 作为
本回合扣血，形式大致是：

```text
damage[player] = 对手 FightReport 的 Score
hp_next[player] = hp_current[player] - damage[player]
```

`round 0 -> round 1` 的初始化边界需要单独处理；从后续回合开始，
`reactorCore` 本身就是快照中的当前血量。2v2/多人局还需要另外确认 Score 的
归属和结算规则。

### 但 action 与快照的时间边界要注意

同一个 `PlayerRoundRecord` 中：

```text
playerData(round i) + actions(round i)
    -> 布阵后的 units_fight / 本回合战斗
    -> playerData(round i+1)
```

`playerData(round i)` 是部署动作之前的状态，所以本回合新买的单位不会直接出现在
同一条 `units` 里。仓库转换器生成的 `units_fight` 是把 `BuyUnit`、`MoveUnit`、
`UpgradeUnit` 叠加到快照后的派生结果，不是原始回放字段。

技能也采用累计快照形式：`commanderSkills` 里有技能 ID、`isActive` 和
`coolingRound`；`energyTowerSkills` 保存能量塔技能状态。因此战场技能 CD 可以用
相邻两回合快照直接对拍。

### `preRoundFightResult` 的真实含义

`preRoundFightResult` 位于当前的 `playerData` 中，但语义是“进入当前回合之前，上一
回合战斗的结果”，不是根据当前 `playerData.units` 即时计算出来的结果。对回合 `i`
而言，关系是：

```text
playerData(i) + actions(i)
    -> units_fight(i)
    -> 第 i 回合战斗
    -> playerData(i+1).preRoundFightResult
```

在转换后的训练 pair 中，`p0/p1` 使用回合 `i` 的快照作为输入，标签取
`playerData(i+1).preRoundFightResult`；同一场战斗的 `FightReport` 也记录在下一条
`MatchSnapshotData` 中。`round 0` 和开局初始化相关的记录需要单独处理，不能把其
`preRoundFightResult` 当成普通战斗标签。

因此，当前回合不能只拿 `playerData.units` 直接作为战斗输入。`units` 是部署前快照，
要先叠加本回合的 `BuyUnit`、`MoveUnit`、`UpgradeUnit` 等 action，得到部署阶段结束后
的 `units_fight`。另外，死亡单位虽然仍保留在下一回合 `units` 中，但不能因为它们仍
有记录就认定它们本回合存活；存活/死亡应结合战斗报告及相应的结算语义判断。

### 哪些字段属于 battle simulate

可以把字段按“战斗输入、战斗输出、回合结算”分层：

| 层次 | 主要信息 | 用途 |
|---|---|---|
| 战斗输入 | `units_fight` 中每个单位的 `id`、`Level`、`Exp`、位置、朝向、装备；有效科技；`officers`；塔强化；战场技能；建筑；战斗 RNG；地图/战斗配置 | 决定实际参战单位及其属性、技能、部署位置和战斗过程 |
| 战斗输出 | Win/Lose、存活/死亡、击杀、战后单位 `Exp`/`Level`、`FightReport.Score`、塔/建筑摧毁结果 | 作为战斗结果和 settlement 的输入 |
| 回合结算 | 下一回合 `reactorCore`、`units`、技能 CD、科技/专家/蓝图累计状态 | 更新长期状态；生成下一回合的 state |

其中：

- `reactorCore` 是玩家当前剩余核心血量。它不是单位战斗公式的直接输入，但必须在
  settlement 中用对手的 `FightReport.Score` 更新，并参与终局判断。
- `supply` 是经济。普通战斗胜负不会直接改变它；购买、升级、科技、增援等 action
  以及经济结算会改变它。
- 单位 `Exp` 是战斗相关的持久状态。战斗前的 `Exp` 应作为单位状态输入；击杀或
  参与击杀获得的经验写入战斗结果，并延续到下一回合的单位记录。它影响后续单位
  状态/升级判断，但不属于经济。
- `Level`、单位的 `index` 和 `id` 也要保留：`Level` 影响战斗属性，`index/id` 用于
  把战斗结果映射回跨回合的单位记录。死亡单位下一回合仍在 `units` 中时，不能把
  “仍存在”误解为“仍存活”。

因此，较完整的 battle transition 应写成：

```text
state_i + actions_i
    -> deploy(state_i.units, actions_i)
    -> units_fight_i + combat modifiers
    -> battle result / fight reports
    -> Exp、存活状态、reactorCore、其他结算字段
    -> state_(i+1)
```

### 对“由一回合推出下一回合”的进一步归纳

你的理解可以作为当前 transition 建模的核心假设：对于可观测的
`playerData`，大部分字段都可以由本回合快照和 `actionRecords` 经过确定性的部署、
购买、升级、科技、技能 CD 和累计状态计算推出。可以抽象为：

```text
playerData(i) + actionRecords(i)
    -> deterministic_state_update
    -> battle_result(i)
    -> playerData(i+1)
```

在这个分解中，battle result 主要影响：

1. `reactorCore`：根据本回合受到的核心伤害更新剩余血量；
2. `preRoundFightResult`：把本回合的 Win/Lose 写入下一回合快照；
3. 单位累计 `Exp`：根据击杀/参与击杀等战斗事件增加经验，并把战后经验带入下一
   回合单位记录。

死亡单位不会因为战败而从下一回合 `units` 中删除，所以单位记录集合本身可以由
原有记录和本回合 action 延续；但“哪些单位实际存活”仍然是战斗结果，不能仅由
   `units` 的存在性判断。

其余字段主要属于非战斗的确定性状态转移或经济/累计状态，例如 `supply`、购买与
升级结果、科技、专家、蓝图、建筑、技能 CD、装备和单位部署位置。这里的“其他”不
应全部称为经济：位置、科技、专家、技能 CD 等是 action/state 累计，不是经济数值，
但通常不需要 battle simulate 才能得到。

最后，若目标是逐字段复现原始 `playerData`，`randomStateData` 需要单独列为 RNG
状态处理；它既不是经济字段，也不能简单地归入上述三个 battle 结果字段。开局
`round 0 -> round 1` 的核心血量初始化同样需要单独处理。

### 对 transition 的实际判断

回放足以验证下面这类分层 transition：

```text
state_i + action_i
    -> pre_battle_state_i
    -> battle/settlement
    -> expected_state_(i+1)
```

但还不能把当前 `playerData` 原样称为“完整的无后效性 battle field”，原因有三点：

1. `reactorCore` 是当前玩家剩余血量，但 `round 0 -> round 1` 是开局初始化边界，
   不能把它和普通战斗扣血放在同一个简单公式里；
2. 增援候选项属于全局 `matchDatas/MatchSnapshotData/reinforceItems`，不在双方的
   `playerData` 内；当前转换后的 `rounds.json` 主要保留了已选 action，未把每回合
   的完整候选列表都挂到 state 上；
3. `officers` 是 ID 列表，能表达“拥有谁”，但不能单独表达每个 ID 的语义以及
   哪些效果是永久的、哪些是本回合一次性的。一次性效果还要结合 action、技能状态、
   `supply` 或单位快照判断。

所以建议把 transition 的 state 定义为：双方 `playerData` 快照 + 当前回合的
`MatchSnapshotData` + 开局初始化规则/终局字段。这样，`reactorCore` 可以直接作为
next-state oracle 中的当前血量；只需对 `round 0 -> round 1` 的开局修正单独建模。
