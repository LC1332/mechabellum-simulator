# 强化学习准备度评估与后续路线图（2026-08-27）

> 评估范围：当前仓库的 `pysim` 战斗引擎、`pysim/transition`、回放数据管线、
> `/game` 审计游戏、测试与现有 RL 文档。
>
> 本报告只做现状判断和计划设计，不包含代码实现。`/game` 的基本体验已经由用户人工
> 验收，本报告不重复评价 UI 还原度，重点判断它能否作为下一阶段强化学习的基础。

## 1. 结论先行

### 1.1 总判定

当前项目已经跨过了“只有战斗模拟器”的阶段，具备立即启动下一阶段 **RL 工程准备、
离线数据集、Value baseline 和行为克隆**的条件；但尚不具备直接启动“完整 Normal 1v1
端到端多回合 self-play”的条件。

分层判定如下：

| 目标 | 当前判定 | 说明 |
|---|---|---|
| RL 接口与数据工程 | **可以立即开始** | 结构化 state/action/outcome、连续 transition、回放正规化和审计工具已经存在 |
| 单回合 `V_battle_real` / `V_battle_sim` baseline | **可以立即开始** | 真实标签和 pysim 标签已有，但要先冻结输入视图、domain 和数据切分 |
| `pi_BC` / action generator | **可以开始准备，训练前有 P0 gate** | canonical action 已有；RL 观测、语义动作、prefix mask 和训练轨迹还没冻结 |
| 受限 `sandbox_v1` 的小规模 RL | **修完 P0 后可以开始** | 闭环已能跑，但合法动作、确定性、save/load、reward 和 soak gate 尚未真正通过 |
| 单回合候选搜索 / best-of-N | **在 BC 与 Value baseline 后开始** | 可以直接用 pysim 评分，Value 先做预筛和排序代理 |
| 完整 Normal 1v1 多回合 self-play | **现在不要开始** | 完整 phase/offer 尚未收进统一 env，装备等机制仍是硬墙，严格可玩前缀不足 5 回合 |
| 声称策略能迁移到真实游戏 | **现在不能** | 真实历史回合胜负一致率约 56.9%，必须保留 sim/real 双域和 exploit 防线 |

一句话概括：

> **可以开工，但应把下一阶段命名为“RL-0：环境契约硬化 + 离线 baseline”，而不是
> “正式多回合强化学习”。**

### 1.2 对“先建立 action 生成函数和 V 函数”的修正

这个猜想方向基本正确，但需要三处修正：

1. action 生成不是一个孤立的 `generate_action(o)`，而是
   **观测编码 + 分层动作 grammar + 每个 prefix 的规则 mask + prefix 执行状态**；
2. `V` 不是 reward，也不是一个含义统一的函数。至少要先分成
   `V_battle_sim`、`V_battle_real`，后面才有 `Q_round` 和 `V_episode^pi`；
3. 在 cheap simulator 可以直接运行时，第一版候选比较应优先使用真实 pysim 结果。
   Value 的作用是预筛、排序、校准和降低大候选矩阵成本，不应一开始就替代 simulator。

因此推荐的近期并行关系是：

```text
                         ┌─> V_battle_real baseline
RL contract + dataset ───┼─> V_battle_sim baseline
                         └─> canonical action dataset ─> pi_BC/action generator

pi_BC + Value + direct pysim ─> 单回合 best-of-N / 对手候选矩阵
```

## 2. 为什么现在已经具备“开始下一阶段”的基础

### 2.1 环境骨架已经成立

当前仓库已经有以下 RL 环境核心构件：

- `EnvironmentState`、`PlayerState`、`UnitCard`、`CanonicalActionPlan`、
  `BattleOutcome`、`StepResult` 均为结构化对象，并带
  `schema/ruleset/engine` 版本；
- `TransitionEnv` 已有 `reset`、`observe`、`step_joint`、单动作执行、battle、
  settlement、advance round、save/load 的基本接口；
- battle adapter 已建立长期 `entity_id` 与战斗内 card 的映射，可回写逐卡经验；
- settlement 已能结算 HP、经验、终局和零和 reward；
- state 有 canonical serialization、digest、diff 和不变量检查；
- raw replay actions 已经去 Undo/Cancel 正规化，并有稳定单位引用和审计报告；
- `/game` 已证明 transition 可以成为服务器唯一真状态，而不是每回合从未来快照回灌。

这意味着项目已经完成了最难的概念跃迁：

```text
battle(f0, f1) -> result
```

已经扩展为：

```text
state + joint plans
  -> deployment transition
  -> one battle outcome
  -> settlement/reward
  -> next-round state / terminal
```

### 2.2 外围 transition 已经有较强的回放证据

现有全量报告给出的关键数字：

| 指标 | 当前结果 | 对 RL 的含义 |
|---|---:|---|
| Undo / Cancel 折叠 | 16680 / 1848，零 crash | canonical action 数据不必学习人类撤销轨迹 |
| `unresolved_refs` 非空回合 | 48/20282 = 0.24% | 绝大多数历史动作能建立稳定引用 |
| unitIndex 顺序计数器 | 99.70% | 新单位的长期引用基本可复现 |
| spawn 集合 | 99.54% | 购买/赠予实体生成链已较可信 |
| 部署 unit-set exact | 85.3% | 全量仍有未知机制/经济污染 |
| 干净回合部署 exact | 99.03% | 可以先建立高置信训练子集 |
| settlement oracle：HP/胜负/经验 | 100% / 100% / 100% | 战后外围结算可以作为强 gate |
| `supply_exact_rate` | 36.6% | 历史经济状态仍需过滤/标记，不能无条件拿来做 legality 标签 |

这里最重要的不是追求“全量 100%”，而是已经能把：

- 规则明确且 exact 的样本；
- 不支持机制导致的覆盖缺失；
- 经济残差；
- 引用解析失败；

分开报告。这个能力足以支撑高置信数据集和逐步扩展。

### 2.3 `/game` 的验收价值

用户对 `8300/game` 的体验验收，提供了自动测试不能完全替代的证据：

- 状态、动作、战斗和结算的组合在人类看来已经接近原游戏；
- 逐动作交互能够刷新合法操作和权威状态；
- 多层审计信息足以定位错误，而不是只能看最终胜负；
- transition 已经可以承载真实的策略操作，而不只是离线重放。

但这项验收证明的是“交互闭环和基本体验成立”，并不自动证明：

- 模型观测没有缺字段或泄漏；
- action prefix mask 完全正确；
- 1000 局随机策略无状态错误；
- save/load 后 RNG、收入债务、offer 状态完整恢复；
- reward 已经适合作为 Value/RL 标签；
- pysim 中学到的优势能迁移到真实游戏。

两种验收是互补关系，不应互相替代。

## 3. 当前还不能直接做端到端 RL 的 P0 缺口

以下不是“模拟器不能用”，而是“在大量生成训练数据前必须先冻结”的契约问题。

### 3.1 RL Observation 尚未冻结，而且当前接口有 handle 语义不一致

`TransitionEnv.observe()` 当前只包含一部分字段：回合、phase、HP、supply、单位、
解锁、科技、officer 和对方单位/HP。它还没有完整表达：

- max HP；
- 双方塔强化；
- 蓝图；
- 指挥官技能、CD 和本回合释放；
- 装置、建筑；
- 装备；
- opening / reinforcement offers；
- 对方哪些经济、科技、技能信息真实可见；
- ego-centric 坐标镜像；
- hidden RNG / 牌池历史是否需要从 observation 排除。

更关键的是，目前 `observe()` 把单位 handle 输出为单位在 tuple 中的枚举位置 `j`，
`handles()` 也返回 `0..n-1`；但 deploy 的 `_find_unit()` 实际按 `replay_index` 解析
`EntityRef.handle`。在连续购买、赠予、出售或非连续 replay index 后，两者不保证相同。

这对网页单动作交互影响不大，因为 `/game` 的 `GameView` 直接暴露 `replay_index`；
但对 RL policy 是硬契约错误：模型按 observation 给出的 handle 输出动作，环境可能指向
错误单位或返回 `UNKNOWN_ENTITY`。

**Gate：**定义唯一的 `ModelObservationV1` 和 observation-local handle 映射；同一次
observation 内 handle 唯一、稳定、可逆，执行只使用该映射，不暴露永久 entity ID。

### 3.2 当前 legal candidates 不是“action prefix 条件下”的合法性

现有 `legal_action_candidates(player)` 对单个当前 state 能列出一部分候选，但
`RandomLegalPolicy.plan()` 在不执行 prefix 的情况下，连续从同一个旧 state 取候选，
最后把整串计划一次提交。

本次审计实际运行：

```text
python examples/random_rollout.py --episodes 1 --seed 7

episodes 1 | done 1 | crashes 0 | 11.4~11.6s
rounds mean 7.0 max 7
failures: {'rejected:INSUFFICIENT_SUPPLY': 20}
```

相同 seed 复跑两次，摘要相同。问题不是环境随机崩溃，而是计划里的多个动作分别在
旧资金上都“看起来可买”，累计执行后资金不足。这说明当前的 random policy 虽然名为
`RandomLegalPolicy`，却还没有满足“生成的每一个 prefix 都合法”。

类似风险还包括：

- 多次购买的 `new_ref` 分配依赖 prefix 状态；
- buy limit、科技前置、售出后的 handle、蓝图顺序效果都依赖 prefix；
- 当前候选只覆盖 buy/move/upgrade/tech/unlock/end 等子集；
- tower、blueprint、skill 等已支持行为仍以 `RAW_UNSUPPORTED + raw_type` 进入 transition，
  不适合作为最终模型 action grammar；
- move 候选使用抽样 10×10 网格，购买仅给三个固定落点，这只是随机探针空间，不是
  已冻结的策略动作空间。

**Gate：**action generator 每生成一个原子动作，都必须在 shadow/prefix state 上执行，
再从新 state 生成下一个 mask，直到 `END_DEPLOY`。合法候选与真实执行必须共用同一规则源。

### 3.3 Reward 虽然零和，但规格尚未冻结

当前 `settle_transition()` 使用：

```text
r0 = damage_to_player1 - damage_to_player0
r1 = -r0
terminal win/loss 再加 +/-1
```

它满足严格零和，但与现有 `rl-roadmap.md` 中“按双方 max HP 归一化的扣血百分比，
终局再加 +/-100%”并不一致。当前一回合伤害通常是数十或数百，terminal 的 `+1`
几乎没有尺度意义。

在训练任何 `V_episode` 或策略梯度前，必须冻结并版本化，例如：

```text
r_damage  = damage_to_opp / max_hp_opp - damage_to_self / max_hp_self
r_terminal = win_bonus - loss_bonus
r_total   = r_damage + lambda_terminal * r_terminal
```

或者明确采用纯终局胜负作为 episode target、扣血只作为辅助 shaping。无论选哪种，都应
返回逐分量并记录 `reward_version`，不能只保留一个无版本 scalar。

同时需要纠正文档中的一句概念：

> reward 是环境规则；`V^pi(o)` 是在策略 `pi` 下从 `o` 出发的期望累计 reward。

`V` 不是“本质是定 reward”。如果部署前局面还没有给出双方动作，Value 一定隐含了
后续策略分布；只有 `V_battle(pre_battle_state)` 更接近确定局面的 outcome predictor。

### 3.4 Seed、save/load 和确定性尚未达到训练级 gate

已有的正面证据：

- 同一显式 `battle_seed` 的 battle outcome 有测试；
- state serialization round trip 和 digest 有测试；
- opening 和 `/game` battle seed 有确定性来源；
- 回放正规化两次 MD5 一致。

仍需补齐：

- `TransitionEnv.reset()` 目前接收 state，不接收 ruleset config + seed；
- `battle_seed=None` 时使用 Python 全局 random，不是环境自己的可保存 RNG；
- `save()` 只保存 state、income policy 名字、battle opts、max round；
- `load()` 实际只恢复 state，没有恢复 income policy 内部的快速补给债、环境 RNG、
  已用收入、offer/牌池状态；
- `test_env_episode_and_save_load` 的关键比较带 `or True`，目前不能证明续跑轨迹相同。

**Gate：**任意回合保存后恢复，给出同样的双方 action，后续所有 state/reward/outcome
digest 必须与不中断运行逐字段一致；snapshot 必须包含所有会影响未来的隐藏状态。

### 3.5 Trajectory 还不是训练数据契约

`replay_player_match.py` 已记录版本、seed、receipt、damage、reward、经验变化和 digest，
这是很好的审计起点；但没有完整保存每步 observation 和 canonical action 内容，
`deploy_digest_before` 仍为 `null`。

`random_rollout.py` 的 report 更轻，只保存 episode 摘要，且最多写前 20 个结果，不能：

- 重放具体 action；
- 逐 prefix 验证 mask；
- 形成 `(O, A, R, O', done)` 训练样本；
- 做 save/load 续跑对照；
- 绑定完整 env/policy/battle seed 子流和 git/data 版本。

**Gate：**冻结 `TrajectoryV1`，至少包含 initial snapshot、每个 observation、合法 mask
摘要、原子 action、receipt、state digest before/after、battle outcome、reward 分量、
done/stop reason、所有版本和 seed。

### 3.6 1000 局 soak 与吞吐基线尚未通过

现有路线要求 RandomLegalPolicy 1000 局无 crash、reject、NaN、负资源、重复 ID 和 phase
错误。目前没有仓库内可核验的 1000 局报告；本次审计的一局已经出现 20 个 stale-mask
拒绝，因此该 gate 明确未通过。

本次 1 局、7 回合耗时约 11.5 秒。10/100 局探针在审计等待窗口内未完成，脚本也没有
中间进度，因此没有把未完成运行当作性能结论。正式训练前应先报告：

- battle/s、environment step/s、episode/h；
- 按回合、单位数、科技/技能数量分桶；
- action candidate 构造耗时与 battle 耗时；
- 多进程扩展效率；
- best-of-N 和 `N×N` 候选矩阵的预算。

这会直接决定 Value 是“可选加速器”还是搜索必须依赖的预筛器。

### 3.7 完整 Normal 1v1 仍未闭合

`/game` 的会话层已经有 opening、reinforcement、deployment、round result、blocked、
terminal 流程；但底层 `TransitionEnv.Phase` 仍只有 deployment/pre-battle/settlement/
terminal。换句话说，完整游戏 phase 目前由 web session 编排，不是统一 RL env 的一步。

全量 game library 的当前严格边界也很清楚：

- 1106 局、2010 个玩家/对手选项；
- 严格可玩到 5 回合的选项为 0；
- 当前最佳可玩前缀为 R4；
- 主要硬墙是装备卡，其次是部分能量塔技能、装置和未映射战场技能；
- first blocker 大量发生在 R1；
- 从真实规则独立 `reset()` 后生成完整 opening/reinforcement 牌池，仍没有作为统一 env
  的标准能力。

这不阻止受限 sandbox RL，但必须把 ruleset 明确命名为 `sandbox_v1`，不能把它的结果
包装为完整 Normal 1v1。

## 4. 战斗模拟器保真度对 RL 的影响

当前两组数字要同时保留：

| 评估分布 | 结果 | 正确解读 |
|---|---:|---|
| 8 个机制/阵容 benchmark | 1793/2349 = 76.3% | 局部机制和指定阵容覆盖已有较好基础 |
| 真实历史回合 | 4053/7122 = 56.9% | 更接近策略实际访问的分布，是 RL 的主要风险指标 |

真实历史回合还呈现随局面复杂度上升而下降的趋势：r1-2 约 60.9%，r7+ 约 53.2%。
这意味着多回合 RL 恰好会在模拟误差更大的后期局面上积累策略偏差。

因此：

- 可以在 pysim 内学习和验证搜索/RL pipeline；
- 不可以把 `V_sim` 当成真实游戏 Value；
- 训练数据必须带 `domain=sim|real`；
- 必须分开 `V_battle_sim` 和 `V_battle_real`；
- 高收益异常策略必须进入 simulator-exploit 回归集；
- 评估要按回合、兵种、科技、技能和局面规模分桶；
- 后续真实 query 应优先挑选 sim/real 分歧大且会改变策略选择的局面。

## 5. 对现有 roadmap 的状态重判

现有 `rl-development-plan.md` 的阶段设计总体仍合理，但状态已经落后于代码；
`rl-roadmap.md` 中“transition 尚未实现，是最重要的下一步”已经过时。

建议把当前里程碑重新标记为：

| 原阶段 | 当前重判 | 证据 / 未完成项 |
|---|---|---|
| M0 规则与数据审计 | **基本完成** | 全量 action census、Undo 语义、经济/引用/开局/增援探针已有 |
| M1 State/Action 契约 | **核心完成，RL 视图未完成** | 内部 schema/digest 已有；Observation、handle、完整语义 action 未冻结 |
| M2 Deployment Transition | **受支持子集完成** | 干净回合 99.03%；全量 85.3%，未知机制和经济残差仍存在 |
| M3 Battle + Settlement / env MVP | **代码闭环已存在，验收未通过** | HP/经验/零和/终局已有；prefix legality、reward v1、save/load、trajectory、1000 soak 未过 |
| M4 完整外围规则 | **部分完成** | `/game` 垂直切片成立；严格 5 回合为 0，完整 phase/offer 未统一到 env |
| M5 序列/tokenizer | **未开始** | 结构化 canonical 是基础，但无 ModelObservationV1、grammar round trip |
| M6 数据与 baseline | **数据源已具备，标准产物未完成** | 1106 局/8228 标签回合；缺无泄漏 split、manifest、baseline 报告 |
| M7 监督模型 | **未开始** | 应先上小型 baseline、`pi_BC`、sim/real 双 Value |
| M8 单回合改进 | **未开始** | 等待可执行 action generator 和稳定评分 |
| M9 多回合 self-play | **未开始且不应抢跑** | 等待受限 env gate，完整 Normal 还需 M4 |
| M10 sim-to-real | **评估意识已有，训练闭环未开始** | benchmark 已有，尚无双域模型/主动真实 query |

### 5.1 建议删除或修订的旧表述

后续正式更新旧 roadmap 时，建议修订这些观点：

1. “transition 尚未实现”改为“`transition-v0.3` 已形成受限闭环，正在做 RL contract
   硬化与完整 Normal 扩展”；
2. “V 最重要，本质是定 reward”改为“reward 先版本化；Value 按 battle/round/episode
   和 sim/real 拆分”；
3. “模拟器完备后直接上多回合”改为“先单回合 BC + direct-sim 搜索，再做受限多回合，
   最后合入完整 Normal”；
4. tokenizer 不应成为所有模型的前置：结构化 Value baseline 可以先做，只有自回归
   action policy 需要冻结完整 grammar/tokenizer；
5. 把 simulator fidelity 作为与 policy 学习并行的长期轨道，而不是最后才处理的 M10。

## 6. 修订后的双轨 roadmap

推荐把后续工作拆成“RL/模型轨”和“规则/保真轨”，在完整 self-play 前汇合。

### 6.1 轨道 A：RL / 模型

#### A0：RL contract hardening（P0，第一优先）

交付物：

- `ModelObservationV1`：可见字段、镜像、排序、handle、offer、隐藏信息裁决；
- `SemanticActionV1`：把已支持 tower/blueprint/skill 从 raw wrapper 提升为语义动作；
- prefix-state action mask；
- `RewardV1` 分量和尺度；
- `EnvSnapshotV1`：包含 RNG、收入债、offer/牌池状态；
- `TrajectoryV1`；
- ruleset/schema/engine/reward/observation/action/data 版本绑定。

完成 gate：

- observation handle 执行 100% 指向原单位；
- 从 mask 采样的 1000 局 action rejection 为 0；
- 1000 局无 crash、NaN、负资源、重复 ID、phase 错乱；
- 相同 seed 完整 trajectory digest exact；
- 任意回合 save/load 后续轨迹 exact；
- reward 零和、逐分量可审计；
- 输出吞吐和规模分桶报告。

#### A1：离线数据集与非神经 baseline

数据集至少拆成：

- `human_action_real`：真实 observation + canonical human plan；
- `battle_real`：真实 winner/damage/fight report 标签；
- `battle_sim`：相同 pre-battle state 的 pysim outcome；
- `transition_exact`：干净且外围 exact 的高置信样本；
- `transition_partial`：带 blocker/残差标签的研究样本。

切分必须按整局、玩家和时间/版本分组，不能随机打散 round。优先建立：

- random legal；
- 不动策略；
- 固定经济 + 简单布阵 heuristic；
- replay action 上界；
- 线性/树模型 battle value；
- 规则统计特征的 win/damage baseline。

当前数据规模约 1106 局、8228 个带真实标签的回合；与 pysim 完整对齐可用 7122 回合。
它足够验证 pipeline、小模型和校准，但不适合从头训练一个大型通用语言模型。

#### A2：第一批模型——`pi_BC + V_battle_sim + V_battle_real`

action generator 建议采用分层自回归，而不是一次输出完整自由文本：

```text
verb
 -> target/mech/tech/card mask
 -> coordinate/orientation mask
 -> apply to shadow state
 -> next verb
 -> ...
 -> END_DEPLOY
```

对位置建议先冻结真实合法格点或分层坐标 head；不要把当前随机探针的 10×10 网格和三个
购买落点直接当作最终动作空间。

Value 第一版拆分为：

1. `V_battle_sim(s_prebattle)`：预测 pysim win/draw/loss 和期望扣血；
2. `V_battle_real(s_prebattle)`：预测真实 win/draw/loss 和期望扣血；
3. 可选 uncertainty / sim-real disagreement head。

暂不训练统一的 `V_episode`。部署前 Value 应等到 policy 分布明确；若输入包含双方计划，
应命名为 `Q_round(o, A, B)`，避免概念混淆。

评估至少包含：

- action grammar 有效率、语义合法率；
- reinforcement/opening 选择准确率；
- 动作类型、目标、坐标、顺序；
- 执行后的 board edit distance、资金差、battle regret；
- Value 的 Brier score、校准曲线、排序准确率；
- 按回合、版本、单位规模和 sim/real domain 分桶。

#### A3：单回合策略改进

建议顺序：

1. 从冻结的历史部署前局面采样；
2. `pi_BC` 为双方产生多样且 prefix-legal 的候选计划；
3. 小候选集直接用 pysim 全量评分；
4. 大候选集用 Value 预筛，再用 pysim 复核 top-k；
5. 先做 best-of-N / rerank，再做近似零和混合策略；
6. 用筛选结果做 rejection sampling、DAGGER 式再训练或离线策略改进；
7. 高收益异常策略全部进入 exploit regression。

Gate 不是只看 sim reward，而是：在冻结对手池上优于 BC/heuristic，同时非法率不升、
策略保持多样性，并在真实标签/`V_real` 上没有系统性恶化。

#### A4：受限多回合 `sandbox_v1` RL

在 A0-A3 通过后，可在明确 feature set 的 `sandbox_v1` 上开始多回合实验：

- 混合真实中间状态 reset 和规则初始状态；
- 训练 `V_episode^pi`；
- 使用 checkpoint league，而非只和最新策略自博弈；
- 保留 human BC/KL anchor；
- 对比多回合策略与逐回合贪心策略；
- 所有 trajectory 可从任意 snapshot 复现。

它的目标是验证 long-horizon pipeline，不是宣称已解决完整 Normal 1v1。

### 6.2 轨道 B：规则完整度与 sim-to-real

建议并行优先级：

1. 装备机制：这是解锁严格 5 回合前缀的最大硬墙；
2. R1 的 ID=0 `ReleaseCommanderSkill` 引用和存量 shard 重建；
3. 能量塔技能 1/3/4；
4. 装置 30001、黏油弹、WayPoint 等高频未映射机制；
5. 把 opening/reinforcement/blocked phase 收进统一 RL env；
6. 建立独立于 replay fixture 的 Normal offer/RNG reset，或明确版本化的外生 offer env；
7. 持续提高真实历史回合 fidelity，并建立不确定性/误差模型。

轨道 B 不必阻塞 A1-A3，但在宣称完整 Normal 多回合 self-play 前必须与轨道 A 汇合。

## 7. 建议的首轮实施计划

### 第 1 阶段：先冻结，不先选大模型

建议先形成一份单独的“RL contract v1 任务书”，把以下问题一次裁决：

1. policy 到底能看到哪些双方字段；
2. player 1 如何镜像；
3. observation-local handle 如何生成和解析；
4. action 是原子 step 还是一回合 plan，prefix state 如何维护；
5. 坐标动作空间的真实离散方式；
6. opening/reinforcement 是否作为独立 phase/action；
7. reward 分量、归一化、terminal 权重；
8. 环境 seed 与 snapshot 包含哪些状态；
9. trajectory 和 dataset 的版本/来源字段；
10. `sandbox_v1` 明确包含和排除哪些机制。

这一步完成前，不建议开始大规模生成随机 trajectory，因为一旦 handle、reward 或
observation 改动，早期数据会整体失效。

### 第 2 阶段：数据和 Value baseline 可以先行

在 ObservationV1 的结构化字段冻结后，可立即并行做：

- 全量 canonical action 数据审计和长度/类型分布；
- 按局/玩家/时间的 train/val/test split；
- `V_battle_real` 的简单统计/树模型 baseline；
- `V_battle_sim` 的同构 baseline；
- sim-real disagreement 分桶；
- battle throughput 和 Value 推理 throughput 对比。

这一步不需要等完整 tokenizer，也不需要等装备机制完成。

### 第 3 阶段：建立可执行 action generator

先训练 `pi_BC`，但评价重点不是 token accuracy，而是：

- 生成的每个 prefix 是否被 mask 保证合法；
- 整个 plan 执行后是否接近人类最终 board；
- 是否能使用当回合买到的新单位；
- 是否学会合理停止；
- 是否在不同对手/回合/版本上保持多样性；
- 送入 pysim 后的 outcome regret。

### 第 4 阶段：做第一个真正的策略改进证明

选一个冻结的历史局面集和冻结对手池，比较：

```text
不动策略
random legal
heuristic
pi_BC
pi_BC + best-of-N direct pysim
pi_BC + Value prefilter + direct pysim top-k
```

只有最后两项稳定优于 `pi_BC`，且没有 exploit/非法率恶化，才算证明“模拟器已经能
推动策略变强”。这比一开始直接上 PPO/self-play 更容易定位问题，也更有研究价值。

## 9. 最终建议

后续计划可以从现在开始展开，优先级建议固定为：

1. **P0：RL contract hardening**——Observation、handle、prefix mask、Reward、seed、
   save/load、Trajectory；
2. **P1：数据集 + baseline**——分域、无泄漏切分、random/heuristic、
   `V_battle_real/sim`；
3. **P2：`pi_BC` action generator**——结构化、分层、mask 约束、执行级评估；
4. **P3：单回合 direct-sim 搜索 + Value 预筛**——先证明策略可改进；
5. **P4：受限 sandbox 多回合 RL**；
6. **P5：与完整 Normal 规则轨汇合后再做正式多回合 self-play 和 sim-to-real。**

所以，对最初问题的直接回答是：

> **模拟器已经具备进入下一步强化学习“准备与监督 baseline”阶段的条件；action
> generator 和 Value 确实是下一批核心产物，但其前面必须插入一个很短、不可跳过的
> RL-contract gate。当前不应直接开始完整多回合 self-play。**
