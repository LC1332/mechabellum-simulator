## 0. 结论先行

下一轮不建议继续平铺低频技能，也不建议立刻对整个移动/索敌系统做大改。
最合适的主线是：

> **以高频动态装备为入口，补齐真实伤害结算、护盾、免疫、回复、吸血和
> 周期召唤管线，再用 1106 局人类回放做按机制的 paired A/B。**

选这一组的原因：

1. 7122 个有效回放回合中，2835 个（39.8%）场上存在装备；1793 个（25.2%）
   含当前未实现的装备战斗效果。这不是边角覆盖。
2. 本轮选定的 11 个 ID 出现于 1628/7122（22.9%）回合；实现后理论上可以使
   1558/1793（86.9%）原“装备效果不完整”回合脱离该 blocker。
3. 卡牌文案已给出大多数主数值，开发不需要猜身份；但护盾溢出、实际伤害、
   免疫时机、回复禁用和召唤时序无法从回放快照推出，非常适合拿到 oracle
   机器做受控实验。
4. 主要改动可以限制在 `engine.py + battlefield/effects + 专项 benchmark/tests`，
   不需改 Transformer 的 observation/action/token/mask，并行边界比布阵权限、经济或技能
   codec 更干净。

本轮的主交付不是“把 registry 从 unsupported 改成 exact”，而是：

```text
equipment_id
  -> 版本化 runtime effect spec
  -> 伤害包/状态/护盾/回复/召唤管线
  -> 可审计 trace 和真实伤害 ledger
  -> 逐装备 oracle A/B
  -> 回放 paired flip 报告
  -> engine 冻结后通知 Transformer 重建 sim labels
```

### 1.3 不能过度解读的统计

- 带某装备回合的原始准确率是关联而非因果；装备更常出现在中后期和强单位上。
- 不得用“这个装备分桶准确率低”直接推断它是错误主因。
- 实现后的可解释信号是同一 pair 在单 ID 开/关时的 winner/card 差异，以及对真实
  oracle 的伤害/存活差异。
- 如果 oracle-correct 的机制使总 winner 准确率下降，不能为了总分把真规则改回去；
  应定位被旧误差偶然抵消的另一个机制。

### 1.4 当前评估键有碰撞

现有 `replay_check` 的 `misses` 使用 `file[:24] + round` 作文本键。在 1106 局中只有
1079 个唯一的 24 字符前缀，存在 25 组重复前缀，最大一组 4 局。总准确率不受
影响，但按机制回连错误样例会混淆。本轮 T0 必须先修评估产物 ID，否则不做
“某装备修正了 N 对”的结论。

## 2. 目标、成功标准与非目标

### 2.1 必做目标

- 建立稳定 `pair_id` 和逐 pair 结构化结果，支持机制级 paired A/B；
- 将装备定义从“静态四个数值”扩展为版本化 runtime effect spec；
- 建立可区分攻击、DoT、区域、召唤物、屏障与环境伤害的伤害包/记账通道；
- 以实际入血/入盾伤害而非发射前理论伤害驱动吸血与 trace；
- 实现次级增幅核心（前提是先取得数值证据）；
- 实现光子涂层、抗干扰模块的限时减伤和状态免疫；
- 实现便携式护盾、保护屏障、超级屏障；
- 实现汲取模块和纳米维修包；
- 实现坦克/野马/钢球三类生产线，复用统一 summon scheduler；
- 为上述机制采集受控 Windows oracle，未采集的字段保持 provisional；
- 完成无装备零回归、逐装备 oracle、全量回放 A/B 和 Transformer 版本移交。

### 2.2 成功分层

| 层级 | 通过条件 |
|---|---|
| 评估可信 | pair ID 无碰撞，每个 flip 可回连完整回放/回合/机制 |
| 工程完成 | 11 个 ID 有明确 runtime spec、trace、feature flag、测试和 registry 状态 |
| oracle 完成 | 必做交互的 A/B 采集齐全，数值/时序/层级在容差内 |
| 覆盖完成 | 当前语料的 unsupported-equipment 回合从 1793 降至约 235（以重生成报告为准） |
| 回放有效 | 选定 ID 分桶的 card/winner 误差有净改善，且收益不来自非法伤害/召唤泄漏 |
| 可冻结训练 | engine/version/report 冻结，Transformer 方可重建正式 sim labels |

“工程完成”不要求总 winner 必须上升。如果机制对 oracle 更准但 winner 下降，任务
应以“发现了新的补偿误差”结项，不对真实规则做 leaderboard 拟合。

### 2.3 明确非目标

- 不在本轮修改 `pysim/rl/**`、Transformer token/model/loss/mask；
- 不实现部署模块 `13040001`，因其属于 placement/action legality；
- 不实现统御核心 `13030010`，因其同时改资金、战斗属性、死亡触发和终局；
- 不为当前语料仅 0–1 回合的先进寄生弹药、先进酸性弹药、深渊信标、
  试验级巨山装甲、应激电容扩张专用分支；
- 不在同一轮重写整个 `engine.py` 为 ECS/对象引擎；
- 不烘焙 `chaff_xsep`、`beam_pair`、`sw_dive`、泰山双武器等旧开关；可做
  oracle 研究，但实现结论留给下轮；
- 不支持 2v2、特殊地图、非 Normal 1v1；
- 不为了回放胜率默默更改未关联单位基础数值。

### 4.2 分两类取证

**A. 静态反向/数据表取证**

适合确认：

- `13030009` 次级增幅核心的攻击/HP/其他数值；
- 护盾基础值、半径、持续时间、目标层；
- 生产线的首次时间、周期、次数、单次数量、召唤等级和出生 offset；
- 效果标签是乘法、加法、限时 status、shield object 还是 damage hook；
- 一件装备与科技/专家/等级的应用次序。

**B. 逐帧/事件遥测取证**

静态表通常不能回答：

- 护盾只剩 1 HP 时收到 70000 伤害，是抵消整个 hit、仅吸收 1 还是溢出入血；
- 吸血按理论伤害、实际入血、入盾伤害、过杀前还是过杀后计算；
- 光子涂层在 29.9/30.0/30.1s 的边界，以及是否清除先存 status；
- 抗干扰对 EMP 减速、科技失效、骇客转化和核心瘫痪是整包免疫还是部分免疫；
- 维修是从 t=0 就 tick，还是受伤后开始；被引燃/EMP/酸液时是否暂停；
- 跟随屏障的圆心更新频率、覆盖空军与否、多屏障重叠选择；
- 生产单位是否继承 carrier 等级/科技/专家，是否给经验/计分，carrier 死亡后
  队列是否停止。

### 4.3 oracle 输出契约

每帧或固定 tick 至少输出：

```text
t
unit/member id, card id, side, mech, level
position, hp, max_hp, shield_hp, barrier_ref
equipment_id
active_statuses + starts_at + expires_at + magnitude
current_target, attack_state, move_speed, range
damage_event(source, victim, raw, shield_absorbed, hp_damage, tags)
heal_event(source, target, requested, actual)
spawn_event(source_equipment, carrier, mech, level, position)
death_event(killer/source, victim)
winner, end_time, score/fight report fields
```

一个 case 必须同时有 control 和 treatment，固定机制至少复跑 3 次。若召唤位置或攻击
存在随机性，保留 seed 并至少跑 20 次分布；不把一次随机样本写成固定规则。

### 4.5 同机顺带做、但不进本轮代码的研究

下列机制对全局胜率的潜在影响大于某个低频装备，但现有老 benchmark 结论互相冲突，
应在 oracle 机器上做微型场景研究，先不烘焙默认：

1. **爬虫/尖牙阵型、碰撞与拥堵**：`chaff_xsep` 在爬虫库 +4、s28 +7，但 s26 -8。
   需采集前 20s 逐 member 位置、接敌时间、同时开火数和拥堵密度。
2. **索敌、过杀与武器周期守恒**：高频杂兵对所有回合都有影响；应采集 lock/
   retarget/fire/impact 事件，不只看最终 winner。
3. **雷霆、泰山、熔点的多武器/换靶**：已有 `cycle_set +27`、`wc_set=2002:2`、
   `beam_pair=1` 候选，但老库下降 3–6 场。取得事件级证据后再分 case 裁决。
4. **沙虫潜地/钻出**：规则语义已知，`sw_dive` 却使 s25 -4，说明定位/召唤动力学

## 7. 回放因果 A/B 设计

### 7.1 三层对照

1. **单元微型场景**：只验证一个公式/边界。
2. **真实 oracle 对拍**：同场景逐帧对 HP/shield/status/spawn/damage/heal。
3. **1106 局回放 paired A/B**：同一 `pair_id`、seed 和其他 opts，只切换一个装备 ID。

三层不可互相替代。回放 winner 上升不能证明公式正确；oracle 微型场景正确也不能证明
对真实阵容有净收益。

### 7.2 必报回放指标

- 总 winner exact 与 paired bootstrap 95% CI；
- 每个装备 ID 的相关 pair 数、OFF 正确、ON 正确、好 flip、坏 flip、净 flip；
- 一次含多个选定装备的 pair 单列，不在单 ID 因果表重复宣称收益；
- 按 round、carrier mech、carrier level、有/无战场技能、有/无护盾的分桶；
- winner 之外的 end time、双方存活 member/card、card damage/kills 误差；
- 召唤类单列 spawn count/time 和召唤物 damage；
- 装备不相关 pair 的 outcome digest 必须逐 case 不变；
- 所有 flip 保存结构化输入和双臂 outcome，可从报告打开原回放。

### 7.3 准确率与开发选择规则

- oracle 决定规则，validation 回放只用于发现集成 bug；
- 不在同一个 human replay 全量结果上反复试参数并选总分最高的；
- 数值只能从游戏表、oracle 或用户明确冻结中来；
- 正式总回放 test 在配置冻结后只跑一次；
- 如需修改参数，必须新建 run family 并记录理由，不覆盖第一次结果。

#### 12.6.4 偏差扫描方法口径

- 键 = side-observation：(pair, side) 上出现该兵种 / 该兵种+已购科技 /
  该战场技能动作，各计 1 次；同一 pair 双方都有该键时两侧各计。
- `replay_wr` = 真实标签胜率；`sim_wr` = 引擎胜率（draw 计双方负）；
  `delta_pp = sim_wr − replay_wr`，**正值 = 引擎高估（“胜率过高”）**。
- 显著性用 McNemar 式不一致对：over = 仅 sim 胜，under = 仅真实胜，
  `z = (over−under)/sqrt(over+under)`；另报含该键 pair 的 winner 准确率。
- 门槛：兵种 n≥60、兵种+科技 n≥40、战场技能 n≥25。
- §1.3 纪律适用：这是**关联扫描**（该兵种参与的对局），不是因果归因；
  高 z 指向“含该成分的对局引擎系统性判错”，具体误差源仍需 oracle/微型场景
  取证，禁止据本表直接改数值。

#### 12.6.9 与任务书的衔接与纪律

1. 本节全部为**观察性证据**，按 §7.3 不触发任何默认数值修改；上表 TOP
   项应作为 §4.5 research_only 清单的优先级排序输入（雷霆换靶、泰山双武器、
   索敌/过杀、磁暴电磁弧、骇客转化、燃烧弹 rider、飞弹装置、强化训练）。
2. on 臂 winner 净 +3 对不代表“装备 runtime 无效”：29.0% 对局的
   survivors/伤害路径已变；R5 正式对拍仍按 §7.2 报全指标 + 逐 ID flips。
3. baseline 复现已达 bit-exact（4124/7122，逐回合一致），§8.4“不含本轮
   ID 的 pair 逐 case 不变”在全量层面成立（残余 3 键为评估键前缀碰撞，
   非结果差异；pair_id 全 hash 无碰撞）。
4. Transformer 移交提示：sim label 重建后预期 winner label 集变化 ~0.04pp，
   survivors/damage 特征变化 ~29% 对局——value/BC 的特征工程可提前规划
   这两路信号。
